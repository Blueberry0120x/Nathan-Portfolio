How I built it

The problem

From a folder nobody could navigate to a catalog you can search

A CAD team piles up LISP the way a garage piles up tools: useful, but scattered, undocumented, and impossible to search. The best routines get buried, and the same command gets written again because no one knew it was there. The library needed a map, so that is what I built.

Before · scattered

Routines with no map

Dozens of .lsp files across a master library that keeps changing. No search, no categories, uneven headers, and no way to see what exists or how the commands relate. You found things by asking around.

After · the catalog

One JSON file, two views that always match

A pipeline reads every (defun c:…) block into one catalog, then builds a searchable list and a 3D command map from that same data, so the two views always agree.

sync → inspect → stage → build  ·  a harvest I can rerun, not a one-time cleanup

There is also a 10-dimension code-standards scorecard that grades 43 files, and a cross-command analyzer that maps how the routines relate. Together they turn "a pile of scripts" into a catalog that can be maintained and audited.

How it runs

Four stages, no hand-made list

Nobody edits the catalog by hand. It is generated from the source on every run, so it stays true to the code. Each of the four stages stops a different way a hand-kept index goes stale.

Sync
Mirror the source, read-only. A one-way copy of the LISP master library into a working mirror, so the source is never touched.
Inspect
Drift report. Compare the source against the mirror so the catalog never falls behind the real library without anyone noticing.
Stage
Keep the real files. Keep the library files that belong in the catalog and drop the scratch and legacy files.
Build
Parse → JSON → viewers. Read every (defun c:…) into CommandLibrary.json, then render both viewers and the standards scorecard from it.
